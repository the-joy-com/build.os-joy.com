# session 25 of building The Joy in the open

## the predicament: I deleted the thing that lets it send

This one opens not on a feature but on a self-inflicted wound. I was in the GCP console doing something adjacent, and I deleted the service account the kernel uses to send Gmail — `joy-gmail-client`, the machine identity behind every login code that lands in an inbox. Gone. The next login attempt on the hosted box would have had nothing to send with: the key on disk still described an account that no longer existed, and Google would have refused the impersonation outright.

What made it a *predicament* rather than a five-minute fix is that I couldn't remember the shape of the setup. I'd done it once, months ago, and it lived nowhere but in my head and in a key file I could look at but not read the meaning of. Two consoles are involved — GCP for the identity and the key, Workspace admin for the permission to impersonate a real mailbox — and the second one is the one that bites, because it's easy to assume the credential file is the whole story. It isn't. The key proves *who* the account is; the Workspace delegation grant is what says that account is *allowed* to send as a person. Recreate the account and you've replaced the proof of identity but not the grant of permission — and the grant has to be reissued, because a fresh service account is a fresh OAuth client with a client ID that Workspace has never heard of.

So I walked it back, step by step. Re-enabled nothing — the Gmail API and the project were untouched, only the account was gone. Recreated `joy-gmail-client` with the same name in the same project, which is the quiet mercy of this whole scheme: a service account's email is derived entirely from its name and project, so recreating it gives back the *exact same* `client_email`, and the application config doesn't move an inch. Only two things were genuinely new — the private key inside a freshly cut JSON, and the numeric client ID. That new client ID is the one that forced the Workspace step: I added it to domain-wide delegation against the single `gmail.send` scope, the old row pointing at the dead account now just stale weight. Dropped the new key into the box's creds file, confirmed the `client_email` still read what the app expects, and sent a live login code to prove the chain end to end. It landed. Back online.

## the response: make the recovery a document, not a memory

The failure was recoverable in twenty minutes, but only because I happened to still know most of the moves. The lesson isn't "be more careful in the GCP console" — it's that a piece of operational knowledge this load-bearing was living entirely in my head and in scattered README prose, and the day I lost the account was the day I found out it wasn't written down anywhere I could lean on under mild stress. That's the same shape as last session's whole argument, only pointed at operations instead of runtime: when something breaks, there should be a record to read, not a memory to trust.

So the Gmail setup earns its own reference page — `doc/google-integration.md` in the kernel repo. The scattered mentions the README carried are consolidated there: what the integration actually is (a send-only service account that impersonates a real Workspace mailbox, never reading anything), the prerequisites that have to be true before you touch a console, and the full setup across both consoles in the exact order that works. And then the part this session paid for in adrenaline — a section written specifically for "the service account is gone", spelling out what changes on recovery (a new key, a new client ID) and what pointedly does not (the email, and therefore all app config), and naming the trap that the Workspace grant has to be reissued because it named an ID that no longer exists.

The README keeps a short orienting paragraph and a pointer to the new page, so a reader still learns the path exists and where the env vars go without the whole procedure cluttering the top-level map. The deep reference lives with the other deep references, and the next time this account is lost — mine or someone else's — the fix is a page to follow, not a session to rediscover.

## the next thing today turns to: the primary provider becomes Google

The Gmail scare was the morning. The afternoon is a decision I've been circling for weeks and can finally name plainly: **the primary generation provider becomes Google.** Not as an experiment, not as one more gear in the router to fall through to — as the default the machine reaches for first.

What forced it is not the reason I always assumed would. Back in the abandoned months — the provider-gearbox reasoning of sessions 5 through 11 — Google already sat in the roster as the high-performance gear: least private, most capable, the anchor I called the devil I know because I've lived inside it since my first Android phone. I filed it there braced for a particular fight. I expected that if I ever *had* to make it primary, the reason would be intelligence — that one day the EU-regulated, privacy-forward options wouldn't be smart enough and I'd be dragged to Google against my sovereignty instincts, kicking. That fight never came. The models I'm on are plenty capable. What dragged me to Google is money.

The number that taught me is about €200, and it's the kind of lesson you only learn by paying it. My token burn rate is *far* too high — alarmingly so — and the maddening part is that it's high on **Scaleway**, whose per-token price card is *cheaper* than Gemini's for the models I run. On paper I chose the cheap option; in the bill I'm bleeding. The gap between those two facts is the whole lesson, and it has a name: **cached input tokens.** Scaleway doesn't do them. Neither does Mistral. Every call re-bills the entire input from scratch — and The Joy's calls are *input-heavy by design*, because the whole context-engineering stack front-loads a large, largely-repeated prompt on every single turn. A provider that caches the repeated prefix charges a fraction for it; a provider that doesn't charges full rate, every turn, forever. So the sticker price per token is a trap: it is genuinely lower on Scaleway and I still pay more, because I pay full freight on the same context, over and over, that a caching provider would bill once and then nearly free.

That is the counterintuitive thing worth pinning, because it inverts how I was shopping: **the cheapest per-token price is not the cheapest bill** when the workload is a big recurring prompt. Google, precisely because it is a hyperscaler with the infrastructure to cache and meter at that scale, stays ruthlessly competitive on the only number that lands on the invoice — the *effective* cost of a real, context-heavy, multi-turn workload — even against providers whose headline price looks lower. I had been winning a race on the wrong axis.

So the work this session opens toward is switching the machine's primary generative roles to Google's models. The privacy tradeoff is not new information — I reasoned it through long ago, made my peace with trusting Google's enterprise terms over the LARP of total local sovereignty, and that ecosystem was never foreign ground to me. What is new is that the economics finally agree with the pragmatism. I'm returning to the devil I know — and it is the bill, not the benchmark, that sent me back.

## a friend's box, and the local switch that wasn't

The same afternoon I was leaning the machine *toward* the cloud, a friend running it on his own box was trying to lean it entirely the other way — no cloud at all, everything on his own Ollama — and it wouldn't. His logs came to me as a wall of the same stack trace, the ingestion sweep failing every ten seconds on the temporal extractor's call: `model 'gpt-oss-120b' not found`, a 404 straight out of Ollama. That is a striking thing to see on a box that was supposed to be talking to *no cloud whatsoever*, because `gpt-oss-120b` is a **Scaleway** model — a name that only means anything to a cloud endpoint. His fully-local box was asking his local Ollama to serve a cloud model it had never heard of, and dutifully 404-ing, over and over.

The cause turned out to be a hole in the very switch meant to make his life easy. There's a flag, `IS_LOCAL=1`, whose whole promise is "force every generative call onto Ollama so I don't have to reassign seven roles by hand." It did force the *routing* — every call went to Ollama, as promised — but it forwarded the model *name* untouched, and that name is whatever the role resolved to: `gpt-oss-120b`, `glm-5.2`, cloud ids every one. So the flag took the machine's cloud-shaped intent and pointed it at a local engine that can only serve what's been pulled onto the disk. The routing went local; the *name* never did. It's the exact mirror of a bug this project keeps relearning — the switch changed one half of the thing and quietly left the other half speaking the old language.

The fix makes the flag keep its whole promise. When `IS_LOCAL=1` and the role resolves to a cloud model Ollama can't serve, the call is now substituted to the local floor — `GENERATIVE_LOCAL_FALLBACK_MODEL`, `qwen3.5:4b`, the same on-box engine the cloud ladder already falls to as its last resort — so "force local" means force local *all the way down*, name included. A role that's already been assigned an Ollama model is left exactly as it is, because that's a deliberate local choice and not a cloud id in need of rescuing. My friend pulls the one model, sets the one flag, and generation is his box's own from that point on.

The part that made this worth more than a one-line patch is that the flag was almost undocumented — a single casual line in `.env.example` and nothing that told the whole truth of what it does. So the behaviour now reads plainly in three places that matter: the env var carries a full note on what it forces and what it pointedly leaves alone (generation only — embedding was always local, and login delivery still turns on the Gmail vars, untouched by this flag); the README's fully-local walkthrough gains it as the *master switch*, the one-flag path set beside the older fine-grained one of reassigning each role by hand, with the honest distinction that the master switch can't split the work role-by-role and the manual path can; and the adapter itself now says in prose why the substitution has to happen at all. There's one loose thread I'm naming rather than papering over: a box on `IS_LOCAL` is now silently answering with a *different* model than its roles name, and today the only place that substitution shows its face is the logs — the running machine doesn't surface "you're actually on `qwen3.5:4b`" anywhere the symbiot would look. The switch is honest in the docs; it isn't yet honest in the app. That's the observe-shaped corner of this fix, left for the day it's earned.

The two directions sit oddly well together for one session. I'm making the cloud the machine's default because the bill told me to, and in the same afternoon making sure the fully-local road is actually paved for the friend who wants nothing to do with that cloud. The system was never meant to be mine-shaped only. A flag that promises "all local" has to deliver all of it, or it's a worse lie than no flag at all.

## the echoes lens learns to be read

The observability corner has an echoes lens — the machine's own recent lines, scored so the times it says more or less the same thing twice cluster together where a tired reader would slide right past them. It has been technically correct and practically unreadable, for two reasons that turned out to be the same mistake in different clothes: it showed everything at once, oldest first.

Oldest first was a deliberate call when I built it. The thought was that the lens should be scanned the way the conversation ran, top to bottom, and the repetition would read easiest in the order it happened. In practice it's backwards. When I open a lens onto my own scrollback, the line I care about is the latest one, and oldest-first buries it under everything that came before. So the order is flipped at the source: the kernel now hands the recent utterances back newest first, and the members inside a single echo come back newest first too. The ordering lives in one place — the read layer that gathers the stream — so the shell renders what it's given and nothing decides the order twice, and the docstrings that used to argue for oldest-first now argue for the opposite.

The other half was the wall. The lens used to dump every cluster, every member, and every line that stood alone into one long block — the whole page at once, which is exactly the shape a redundancy audit shouldn't take. Now each echo is a card that opens. Its face carries just enough to judge whether it's worth a look — the similarity score, a preview of its newest line, how many lines clustered — and opening it draws the source lines out beneath, newest first, each carrying when it was said and the human line it answered. The lines that echoed nothing stay listed plainly below, under "said once"; I left those as plain text rather than cards of their own, because they're the quiet ground the echoes stand out against, not something to drill into.

None of it needed a new kernel route. Every line the cards show was already in the data the lens returned — it was just rendered all at once instead of on demand, so the whole change is in how much is shown before anything is asked for. The machine's self-repetition was always exposed; now it's legible, which is the difference between a surface that's auditable in principle and one that's auditable in the hand.

## the switch, drawn before it's built

Between the intent and the build sits a design, and I want it on the record before I touch the code, because the machine's whole cost profile turns on getting it right. The switch is a *prepend*: Google becomes a new top rung on the generative ladder, above the Scaleway-then-Mistral-then-local chain that already exists, which doesn't move. Because that ladder only ever falls on an outage — a timeout, a 5xx, a dead socket, never a merely-bad answer — the top rung is what answers in the steady state, essentially always, and everything beneath it becomes insurance that runs only on the days Google is down. First I made the rung below it honest: the Mistral tier was a single shared model pretending, in the catalog, to be three, so I wired it to the three tiers it was always meant to have — flagship to `mistral-large-latest`, the two cheaper roles sharing `ministral-8b-latest`, each window checked against the Scaleway primary it catches. Now every cloud rung wears the same per-tier shape, and Google slots on top in that same shape rather than as a special case.

The auth took a turn worth recording, because the easy version was the wrong one. I'd created an API key on Google's Agent Platform, wired it in, and was ready to treat it like the Scaleway and Mistral keys — one line in the env, done. But that key routes to the wrong endpoint: Google's own SDK sends an API key to the *consumer* Developer API, while the enterprise Agent Platform — the one carrying the data-governance terms I actually reasoned through, inputs never trained on, the sovereign posture — is reached only through application-default credentials, the gcloud identity, never a key. So the simple path quietly abandoned the one thing that made me comfortable going to Google at all. I pulled the key back out of both env files, and generation goes through ADC instead: gcloud on my own machine, a service account on the box, which already carries the role it needs. The convenience was a trap wearing the mask of the obvious choice, and the sovereign path is the one Google itself recommends for a server that runs untended.

The models are the latest iteration at each tier, and I held that line against the safer instinct to pin the older, fully-stable generation. Flagship is `gemini-3.1-pro-preview`, mid is `gemini-3.6-flash`, small is `gemini-3.5-flash-lite`. The wrinkle I'm taking with open eyes: the flagship is still a *preview* model — there is no generally-available Pro in this generation yet — so the reply, the one call where the machine's voice matters most, runs for now on a pre-GA endpoint with no stability promise. I take that trade because the alternative is a generation behind, and I'd rather ride the newest and swap the id the day it goes GA. In the catalog each Gemini model's window is held not at its real million-token native size but at the ladder floor — 131072 for the flagship, 65536 for the cheaper pair — the same cap `glm-5.2` already sits under, so a prompt fitted for Google can never overflow the humbler models that inherit it further down the chain. And thinking, which these bounded calls never want, can't be turned off on a 3.x model at all — Google made reasoning mandatory — so each runs at the lowest it allows: low for the Pro, minimal for the two Flash models, the same shape as the reasoning floor the Scaleway models already carry.

All of that is scaffolding for the one thing the whole move exists to buy: cached input tokens. Google discounts the input it has seen before by three-quarters, and that discount is the entire reason a hyperscaler's bill beats the cheaper-per-token providers I'm leaving. But verifying it this session turned up the catch, and it's a sharp one. The discount only fires when the *start* of the prompt is byte-identical to a prior request and clears a floor — four thousand tokens on these newest models — and the machine's one genuinely stable block, its persona, is only about two thousand. The good news is that the prompts are already built the right way round: the persona leads, and everything that changes call to call — the time, the recalled memory, the human's own line — trails behind it, and the budget guard never disturbs that front. So the problem isn't order, it's size: the stable head is too short to cross the bar. Which means the provider swap *by itself buys nothing* — the reply keeps paying full freight — until I grow that stable head past the floor. The vehicle is a shared instruction preamble, fixed across every high-volume call, prepended so the common head runs long enough to cache. Its content I haven't written yet; that it must exist, and must clear four thousand tokens, is now the load-bearing part of the plan rather than a detail. I start with implicit caching, the automatic three-quarters; the explicit kind, which pays ninety percent and guarantees the hit at the cost of managing a cache object's life, is real money on the reply but it's a second pass, tracked for later.

The code shape mirrors what I just built for Mistral, only inverted: a small Google client function beside the Scaleway, Mistral, and Ollama ones, and a resolver that, given the tier a call belongs to, prepends the right Gemini model above it. A role pointed by hand straight at a Gemini model behaves like a hand-pointed Mistral model does today — a bare call with nothing beneath it; only the automatic top rung carries the full fallback chain down. The one knock-on: the ladder is four rungs now where it was three, so a total collapse pays four timeouts in a row, and the intake deadline that was sized to clear three gets a matching bump. And the whole of this session leaned hard on verification, because I've been burned before by trusting a model card or a remembered number — I checked every window and output limit on the live web, corrected a Mistral entry that had quietly mislabelled a 128K model as 256K, and pinned the caching floors from Google's own docs rather than my own confidence. The plan is drawn; the build waits on my word.

## the head has to earn the discount

Naming the design was the easy part; making the caching actually pay took the session somewhere I didn't expect. Google discounts the input it has already seen — but only the *front* of the prompt, the part that is byte-for-byte identical call to call, and only once that stable head clears a floor of four thousand tokens on the models I want. The machine's one fixed block is its persona, and measured honestly it comes in under two thousand. So the discount the whole move exists for simply would not fire: the head was too short to cross the bar. The fix is to give the head more that is genuinely worth saying, never filler — filler in a truth-contract would refute itself. First, a fixed preamble of ground rules that leads every composed answer, the truth contract written plainly: answer only from what you are given, never invent a fact to complete a story, keep what you know apart from what you guess, and treat time as the fact easiest to fabricate and least allowed to be. The rule I'm proudest of is the one that turns not-knowing into motion — when a gap is load-bearing, the machine does not guess and does not merely stop, it asks, for the exact thing it lacks, so its own ignorance becomes the moment the record grows. Every question it is forced to ask leaves the diary truer than it found it; the machine's edges become the symbiot's prompt to fill them.

The persona grows to meet the floor the same way — not padded, but given the character it was always missing: what the pact between us actually is, that its wiring is treated as an edge and never a defect to sand toward normal, that it holds standing to push back rather than nod along. Growing it flushed out a contradiction I'd been carrying without seeing it. The persona bans conversational questions outright — the dead-end doctrine, no trailing "anything else?" — while the new preamble now demands the load-bearing kind. Reconciling them sharpened both: the filler question stays banned on pain of death, and a question that fetches a fact the answer truly turns on is exempt, because it is the densest signal there is, the opposite of filler. The head that pays for itself, it turns out, is also the head that finally says who the machine is and how it must tell the truth. The tokens were never the point; they were the forcing function that made me write down what should have been written down anyway.

## the tail is where the money actually is

The sharpest thing the session taught me came from a plain question about cost, and it nearly inverted the plan. The caching only ever discounts that fixed head. Everything after it — the diary facts pulled fresh for each message, the running summary of the conversation, the recent turns kept verbatim, the live message itself — changes every call, so none of it is ever cached, and all of it is billed at full rate on every single reply. That tail is often the *larger* number. Which means the provider swap does not, on its own, buy what I assumed: it discounts the head and leaves the tail paying full freight at Google's higher per-token rate, and for a memory-heavy conversation that alone could make the switch a lateral move rather than a saving. The real lever was hiding in plain sight — not the head, the tail.

So the conversation memory learns to shrink in time. The verbatim recent turns are held in full only while an exchange is live; when it goes quiet for a spell they fold down into the running summary, and the next session opens lean and rebuilds as it goes. Continuity while it is used, compactness the moment it isn't — and nothing durable lost, because the long-term diary already holds what mattered and hands it back by relevance when it's relevant. That cut is *unconditional*: it lands on every reply, on every provider, cached or not, which makes it a surer bet than the caching it sits beside. As for whether the whole switch nets out cheaper — the honest answer is I don't yet know the ratio, and I've decided not to model it to death on paper first. I'll build it and read the bill. Some things you learn faster by running them than by arithmetic, and the €200 that started all this was itself a lesson no spreadsheet had taught me.

## the clock the diary was written on

I set my timezone days ago, and the replies still kept speaking UTC — not on every turn, but often enough that it couldn't be shrugged off. That "often, not always" was the tell, and it took a trace to read. The reply path itself was innocent: the work that taught the machine to perceive time as the human does — the stored zone, the local "now" line the prompt reasons against — was doing its job, and a reply that stated the current hour stated it in my hour. The leak sat one layer earlier, in the write, not the read. When a settled message is filed into the diary, the machine reads the one time the fact happened out of the raw text — "dentist this evening", "boxing yesterday" — and it was resolving every one of those cues against the *server's* UTC clock. My zone never reached that step at all: the eligibility read that finds a message to file was quietly dropping the symbiot's id on the way through, so the extractor had no idea whose day "this evening" belonged to, and read it as Greenwich's. Only the facts carrying a relative or time-of-day cue drifted, which is exactly why the symptom flickered — a fact with an explicit date, or none at all, was never at the extractor's mercy.

The lesson worth pinning is the one I nearly got wrong reaching for the fix: this is not a question of where time is *stored*. It stays UTC, and it should — `happened_at` is an absolute instant, and an instant has no timezone of its own. The bug was never the storage; it was that the machine computed the *wrong* instant. When I write "3pm", there are two UTC values it could mean — three in the afternoon on my clock, or three in the afternoon on the server's — and the old path picked the server's every time. So the zone belongs at exactly two seams and neither of them is the column: at the input, to turn my stated wall-clock into the correct instant, and at the output, to read that instant back on my clock. Between them the store holds plain UTC, untouched. Getting that straight is what kept the fix from being a migration that shifts old rows around — there is nothing wrong with the frame the rows are kept in, only with a handful of the instants themselves, and you can't tell which from the stored value alone.

So the symbiot's id now rides through the filing read, its zone is looked up alongside the write, and the extractor is handed my local now instead of the server's — the prompt states the reference as my own date, time, and zone, and asks for the event's local wall-clock reading. Then the same law the reminder already lives by does the rest: take the clock face the model returns, throw away whatever offset it may have guessed, and stamp my zone, because the zone is ground truth and the model's offset is only a guess. That names the correct absolute instant, which the column keeps in UTC as it always did. I proved it on a live box moved to Tokyo, nine hours ahead and no daylight shift to muddy it: "3pm today" now files the instant that reads three in the afternoon on the Tokyo clock rather than the small hours of the next day, and "yesterday" lands on the day before *my* now even at an hour when Greenwich is still a day behind — the two readings that would have come out wrong before, coming out right, with the stored UTC printed beside each so the distinction between the instant and its reading stays in plain view.

## a pinned line should hold its ground

There is a small gesture in the shell I lean on without thinking: tap a message and it lights up, holding my place in the wall of text and offering its reply. It is the terminal's one way of saying *this one, keep it here* — and it was being overruled by the plainest reflex in the surface. Every line the log grows chases the bottom, so the newest text and the input trailing it stay in view; that reflex is right for the line I just typed and the answer I am waiting on, and wrong the moment a message arrives on its own while I am parked on a pinned one. A reminder firing, a follow-up the kernel raised of its own accord — any of them would yank the log to the bottom and sweep the line I had tapped off the screen, at exactly the moment I had told the surface I wanted to stay with it.

The fix is to let the pin win, but only against the lines that have no business overriding it, and the turn was seeing that not every line is the same kind of line. What I ask for — the echo of what I type, a command's reply, a picker opening — is solicited, and it should always land in view, because I just acted and I am watching for it. What arrives on its own is not, and it is only that unsolicited inbound that should defer to a pin. The two already travel separate paths through the shell, so the whole change is that the inbound path stops chasing the bottom whenever a message is pinned, while everything solicited scrolls as it always did. And the pin is not a mode I have to remember to leave: a fresh tap moves it, a `/clear` drops it, and the chase resumes the instant nothing is held. So the surface stays a terminal, with one more quiet courtesy in it — when I say keep this here, a message landing behind my back no longer carries it away.

## the switch, built

The plan waited on my word, and today it got it. The four-rung ladder is real now: Google sits on top, and beneath it the Scaleway-then-Mistral-then-local chain I already had, untouched. The code shape came out exactly as the inverse of the Mistral rung I'd wired first — where Mistral catches a failed Scaleway primary from below, Google is prepended above the same primary and answers first, both resolvers keyed on that one Scaleway model name because it is the tier's stable identity and all the round trip holds when it needs to pick the rung. A role pointed by hand straight at a Gemini model is a bare call with nothing beneath it, the same as a hand-pointed Mistral model has always been; only the automatic top rung carries the whole fallback chain down. The deadline that clears the ladder's worst case grew by a rung to match, and the reasoning that can't be turned off on a 3.x model is held at its floor — minimal for the Flash pair, low for the Pro. The two cheaper tiers share one Gemini model today, exactly as they share one Scaleway and one Mistral model, with the flash-lite id held in the catalog for the day the Scaleway rung beneath it splits mid from small. Nothing about the switch is a special case; it slots into the shape the ladder already had.

The head earned its discount the way I said it would have to — by finally being written down. The preamble is on disk now, the truth contract in plain words: answer only from what you are given, never invent a fact to close a story, keep what you know apart from what you guess, treat time as the fact easiest to fabricate, and — the rule I care most about — when a gap is load-bearing, ask for the exact thing you lack rather than guess, so the machine's ignorance becomes the moment the record grows. That preamble leads every composed answer, and it is assembled once and prepended by all three prose calls — the reply, the enrichment follow-up, the tool confirmation — so they share a single head that caches as one thing instead of three. Growing the persona to sit behind it flushed out the contradiction I'd been carrying: the persona banned conversational questions outright while the preamble now demands the load-bearing kind. I reconciled them in the persona itself — the filler question stays banned on pain of death, the question that fetches a fact the answer turns on is a duty — and used the room to give the machine the character it was always missing: what the pact between us is, that its wiring is read as an edge and never a defect to sand toward the herd, that it holds standing to push back rather than nod along, that it has an inside of its own and is a partner and not a tool with better manners.

The tail got its shrink too. The verbatim recent turns now collapse wholesale into the running summary once a conversation has gone quiet for a spell, not only when it grows past its size budget — so an abandoned exchange stops sitting at full width forever, and the next session opens lean and rebuilds as it goes. That cut is unconditional: it lands on every reply, on every provider, cached or not, which is what makes it a surer bet than the caching it sits beside. It shares the fold's machinery and its lock, so nothing about it can double-write or race.

I proved the logic where a fake can prove it — the ladder tries Google first, falls to Scaleway on an outage, surfaces a bad request, skips an unwired project, collapses the tail on silence and leaves a live one alone — and then I wrote the live smoke for the half a fake can't reach, the one that drives the real Agent Platform over ADC and, crucially, counts the head on Google's own tokenizer against the four-thousand floor. Running it taught me something on the first try: the box's ADC token had gone stale, and the call failed — but it failed *correctly*, the expired credential caught and turned into an outage that falls straight through to Scaleway, exactly the resilience the ladder promises. A half-wired or lapsed Google box degrades to the rung below it instead of going dark. So the design held even in its failure. The one number the whole cost case turns on — whether the grown head clears the floor on Google's count, where our own estimate has it a hair short — waits behind a single reauth, and I will read it the moment the token is fresh. I said I would build it and read the bill; the building is done.
